# LogicBank — Claude Code Instructions

LogicBank is a declarative, transactional business-logic engine for SQLAlchemy — rules (`Rule.sum`, `Rule.count`, `Rule.formula`, `Rule.copy`, etc.) hook SQLAlchemy's `before_flush` event and execute via forward-chaining on commit. It's consumed as the rules engine inside [ApiLogicServer / GenAI-Logic](https://github.com/valhuber/ApiLogicServer).

## Conventions to follow

- **Don't run `genai-logic genai`** in this repo — irrelevant here, it's an ApiLogicServer/GenAI-Logic CLI command, not part of LogicBank's own toolchain.
- **Test via `run_tests.py`, not pytest/Test Explorer** — each example under `examples/<name>/tests` activates `LogicBank.activate()` at import time; running multiple example dirs in one pytest/discovery process causes conflicting activations. See `run_tests_readme.md` → "pytest / VS Code Test Explorer Compatibility" for the full explanation.
- **New example/regression suites get their own folder** under `examples/`, with their own gold DB, models, logic, and tests — mirroring `examples/banking`, `examples/insert_parent`, `examples/multi_relns`, etc. Don't retrofit an existing example's dataset for an unrelated scenario.
- **Multi-relationship-to-same-parent-class bugs are a known fragile area** — `child_role_name=` disambiguation exists on `Rule.sum`/`Rule.count`/`Rule.copy`/`LogicRow.link()`. Before touching any of `aggregate.py`, `sum.py`, `count.py`, `copy.py`, `rule_bank_withdraw.py`, or `logic_row.py`'s `link()`/`get_referring_children()`-adjacent code, read `system/LogicBank-Internal-Dev/multi-relationship-bug-issue-20.md` — it documents the exact failure shape (silent wrong-answer vs. loud fail-fast) and the test discipline required (assert on *all* parent instances touched, not just the expected one) to avoid shipping a fix that looks right but isn't.
- **When you fix a bug here, add a regression test** in the relevant `examples/<name>/tests/` — confirm it fails without the fix and passes with it before considering the work done.
- **`LogicRow.save_altered_parents()` and `listeners.py`'s row-iteration logic are fragile in a specific, non-obvious way** — read `system/LogicBank-Internal-Dev/dragons-deferred-adjustment.md` before touching either. A transaction that reparents a child AND changes a sum-contributing attribute on it in the same commit is order-sensitive against SQLAlchemy's unordered `session.dirty`; the existing defer-on-submitted-parent logic exists specifically to prevent a silent wrong-balance bug that only reproduced ~50% of the time.
- **`AbstractRowEvent._check_and_mark_fired()`'s nesting guard (`row_event.py`) must be cleared at end-of-flush (`listeners.py`'s `after_flush`)** — before touching either, read `system/LogicBank-Internal-Dev/after-flush-row-event-conditions-bug.md`. The guard stores "already fired" state directly on the SQLAlchemy row instance to suppress same-flush re-entrancy (e.g., an `Allocate` cascade loop); if it isn't cleared at the end of each flush, it silently kills every `RowEvent`/`CommitRowEvent`/`AfterFlushRowEvent` on that row for the rest of the session once the row is touched a second time.
- **`Rule.row_event`/`Rule.commit_row_event` activation fails if `calling`'s source appears to write `row.<attr> = ...`** — both fire after that row's `Formula`/`Sum`/`Count`/`Constraint`/`CommitConstraint` processing has already completed for the flush, with no second pass; a mutation there used to be silently persisted without ever being re-derived-from or re-validated. Now caught at `activate()` time (`AbstractRowEvent._check_row_mutation()`, `row_event.py`) via the same textual `inspect.getsource()` scan `Formula`/`Constraint` already use — see `system/LogicBank-Internal-Dev/commit-event-mutation-gap.md` before touching the scan regex or deciding a handler needs `allow_row_mutation=True`. The safe pattern (used throughout `examples/` and `nw_sample`) is read-only handlers, or inserting a *new* row via `logic_row.insert()`/`new_logic_row().link().insert()` (which gets the full cascade and is NOT flagged — mutating `new_logic_row.row.attr` is a different variable's `.row`, not the event's own `row` parameter); mutate-in-place instead via `Rule.early_row_event`/`early_row_event_all_classes`, which fire before that row's own cascade and are exempt from the scan.
- **`parse_dependencies` (`abstractrule.py`) only keeps a 3+-node `row.X.Y` token as a dependency if `X` is a real relationship** (`AbstractRule._is_relationship_node()`) — before touching this method or `find_missing_attributes` (`rule_bank_setup.py`), read `system/LogicBank-Internal-Dev/spurious-parent-dependency-issue-21-31.md` ([GitHub issue #21](https://github.com/valhuber/LogicBank/issues/21)). Without this check, a chained method call on a plain column (`row.code.zfill(8)`) or a paren-stripping artifact from a sub-query (`row.id_customer).scalar()`) gets misparsed as a parent reference exactly like a real one (`row.customer.name`) — either crashing every subsequent update (`"FIXME invalid role name"`) or killing `LogicBank.activate()` for the *entire* rule set, not just the offending rule. Same doc also ratifies the `# deps: row.parent.attr` comment convention (see `Rule.formula`'s docstring) as the supported way to declare a `calling=` formula's parent dependencies when the actual access happens inside a helper function the scan can't see into.
